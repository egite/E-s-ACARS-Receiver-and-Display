The finding that drives the move

xng is better and slower, and the slowness is single-threaded

The original goal was independence from GPL-2.0 acarsdec. Every other VHF ACARS decoder on GitHub turned out to be acarsdec lineage, so the only real candidate is xng — which also replaces GPL-3.0 dumpvdl2, ships an arm64/amd64 .deb, and emits acarsdec-compatible JSON that web/server.py already parses.

It decodes measurably more. It also costs roughly eight times the CPU, and it cannot spread that cost across cores.

At 5 channels xng pins one core and drops samples — 67 stream read: Overflow events in 180 seconds. That was measured with the machine quiet: load 3.0, roughly 250% of the CPU idle. Per-thread sampling found 97.9% on a single tokio-rt-worker out of nine threads. More cores cannot help; only a faster core can.

Decode quality: a four-hour alternating A/B

Both decoders ran healthy at 960 kS/s on two channels, alternating 20-minute blocks so traffic variation averaged out. Zero overflows on either side.

xng led in 5 of 6 cycles; median ratio 1.58, geometric mean 1.70, range 0.64–4.08. Junk is negligible: 31 CRC-bad plus 4 malformed tails out of 1320 raw. Treat +55% as the centre of a range — dropping the single outlier cycle still leaves +25%.

xng filters its own bad frames before UDP. Over a 4 h 25 m soak, 127 of 3462 messages (3.7%) were CRC-bad; they reach the JSONL but not the UDP output. At the matched sample point the log held 3230 CRC-ok and UDP had delivered 3229. web/server.py needs no filtering change.

Target hardware

ASUS Chromebox CN62

The i7-5500U is Broadwell: 2 cores / 4 threads, 2.4 GHz base and 3.0 GHz turbo, with AVX2 and FMA3 — 256-bit SIMD against the A72's 128-bit NEON. Single-thread throughput is the axis that matters here, and it should be roughly 3–4× the Pi's, putting xng's full 5-channel load near 30% of one core.

Firmware flash is required and semi-permanent. It's a Chromebox: open the case, remove the write-protect screw (pre-CR50, the screw completes a ground) and flash MrChromebox UEFI. Leave the screw out. Known trap — Ubuntu often fails to install the grub EFI shim to the default boot target and you land in an EFI shell; MrChromebox's FAQ covers the fix.

USB 3.0 RFI is the real SDR risk. All four ports are USB 3.0; there are none at USB 2.0. USB 3 radiates broadband noise across the VHF range you're listening to. Plan on a powered USB 2.0 hub, shielded cables and ferrites, with the dongles physically away from the chassis. Verify noise floor against the Pi's current figures before declaring the migration good — see step 8.

Stock config is thin. 4 GB RAM is ample (the Pi runs the whole stack in ~1 GB) but the 16 GB SSD is not. Budget an M.2 swap and check the slot type before buying — this generation is M.2 SATA, not NVMe. The box is also 2015 hardware; fan, capacitors and SSD have eleven years on them.

One upside worth noting: SDRplay's API v3 is better supported on x86_64 than ARM, so the RSP1A should behave better for rtl_airband than it does today.

Migration

Procedure

These are ordered because the order matters — firmware before OS, OS before radios, radios verified before any decoder decision.

  1. 01

    Flash firmware, install Ubuntu

    Write-protect screw out, MrChromebox UEFI full-ROM, then Ubuntu Server x86_64. Server, not Desktop — the Pi runs headless at multi-user.target with no X or Wayland at all, and there's no reason to change that.

  2. 02

    Get the files across

    A plain git clone gets the code but not config.json (gitignored), the trial harness, or the project notes. This tarball carries all three — 5.3 MB against the 91 MB a naive tar ACARS/ acars-trial/ would produce.

    # run from /home/pi, not from inside the repo
tar -czf acars-handoff.tar.gz \
  -C /home/pi --exclude='ACARS/third_party' --exclude='acars-trial/xng' \
  ACARS acars-trial \
  -C /home/pi/.claude/projects/-home-pi-ACARS memory

    Excluding third_party/ is not just about size. install.sh's build() skips a component when third_party/<name>/<binary> is already executable. Carry the aarch64 build artifacts over and the installer prints “already built” and skips every rebuild — leaving you with ARM binaries on an x86_64 box. The same applies to acars-trial/xng, which is an aarch64 build; get the amd64 .deb from the release page instead.

  3. 03

    Run the installer

    install.sh is architecture-agnostic as written. Every apt package it names exists on Ubuntu x86_64, and it derives the librtlsdr path at install time rather than hardcoding it.

    cd ~/ACARS
./install.sh

    It installs packages, blacklists the DVB-T driver, builds libacars + acarsdec + dumpvdl2 into third_party/, writes config.json from the example, and installs the three systemd units — substituting @USER@ and @PROJECT_DIR@ into them at install.sh:84, which is why the repo copies differ from what ends up in /etc/systemd/system/.

  4. 04

    Pin the acarsdec revision

    Do this while you're in the installer anyway. install.sh:57 clones master with --depth 1 and no ref, so two installs a week apart get different code with no record of what worked. The Pi is currently on 0b7ba27.

    A side effect of --depth 1: no tags are fetched, so acarsdec's own git describe falls back to a bare hash and it self-reports as Acarsdec 0b7ba27 rather than a version.

  5. 05

    Move the dongles and confirm serials

    The serials are what config.json addresses, so nothing needs renaming if the dongles move physically intact.

    rtl_test -t
#  0:  Realtek, RTL2838UHIDIR, SN: ACARS1
#  1:  Realtek, RTL2838UHIDIR, SN: VDL2_1
  6. 06

    Port config.json

    Copy the Pi's config.json across, then change exactly one thing — the preload path is the only architecture-specific value in it.

    // aarch64 (Pi)
"librtlsdr_preload": "/usr/lib/aarch64-linux-gnu/librtlsdr.so.0"

// x86_64 (CN62)
"librtlsdr_preload": "/usr/lib/x86_64-linux-gnu/librtlsdr.so.0"

    A fresh install.sh run derives this correctly on its own; you only edit it if you copied the file over. Everything else carries unchanged: home coordinates, the two receiver blocks, ports, history_hours: 8, health thresholds, and the VRS URL at 192.168.4.225:6535 — confirm that host is reachable from the new box's network position.

  7. 07

    Bring up acarsdec first, unchanged

    Establish a known-good baseline on the new hardware before introducing xng. Same decoder, same 5 channels, same gains.

    sudo systemctl enable --now acars-decoder@acars acars-decoder@vdl2 acars-web
curl -s localhost:8686/api/stats
  8. 08

    Compare the noise floor before anything else

    This is the step most likely to surface a problem, and the one easiest to skip. USB 3.0 RFI would show as a raised noise floor and reduced message rates that look like a decoder regression but aren't.

    curl -s localhost:8686/api/stats/full | \
  python3 -c "import json,sys;
[print(x['freq'], x['frames'], x['avg_level'])
 for x in json.load(sys.stdin)['traffic']['frequencies']]"

    Pi reference figures, daytime, per 2 h window:

    ChannelFrames / 2 hShareAvg level
    130.45023678.4%−27.2 dB
    130.0254013.3%−37.6 dB
    131.125134.3%−36.9 dB

    Traffic is heavily concentrated: 130.450 alone carries about 78%, and the top three channels about 96%. That distribution held across both overnight and daytime samples.

  9. 09

    Then, and only then, trial xng at 5 channels

    Install the amd64 .deb from the v0.21.0 release. Stop the acarsdec unit first — the dongle is exclusive, and a systemd unit with Restart=always will fight you for it every 10 seconds.

    sudo systemctl stop acars-decoder@acars
xng listen --sdr driver=rtlsdr,serial=ACARS1 --mode acars \
  -g 40 -r 2496000 -c 130.3375M \
  --channels 129.125,130.025,130.450,131.125,131.550 \
  --demod-effort live --udp 127.0.0.1:5550

    Watch for stream read: Overflow in stderr. If the CN62 estimate holds you'll see none, and CPU near 30% of one core. The harness in /home/pi/acars-trial/ (see below) will run a proper soak if you want numbers rather than an impression.

The call to make once it's running

Which decoder to keep

OptionChannelsCPULicensingStatus
acarsdec — no change 5 of 510.8% GPL-2.0 + GPL-3.0 proven
xng, 3 channels 3 of 5 — 96% of traffic45.4% Apache-2.0 / MIT soaked 4 h 25 m
xng, 5 channels 5 of 5~30% est Apache-2.0 / MIT unverified on CN62

The 3-channel option is the fallback that already works — validated on the Pi at 45.2–45.4% across 53 samples, zero overflows, RSS flat at 41 MB. Four channels would need ~1.58 MS/s, extrapolating to ~77% of the single worker thread, which is too close to the overflow threshold to trust without its own soak.

If 5-channel xng holds on the CN62, it is strictly better than today: ~55% more messages, full channel coverage, and permissive licensing for the whole receiver — replacing both acarsdec and dumpvdl2 with one binary.

Things that cost me hours

Traps worth knowing before you hit them

  • acarsdec rewrites its own argv. It tokenizes --output json:udp:host=…,port=… destructively with NULs, so ps and /proc/pid/cmdline show six separate arguments. This looks exactly like a bug in receiver.py and is not one. It also means pkill -f patterns built from the original argument string never match.
  • pkill -f matches your own shell. It bit me twice — once killing the shell running the kill, once killing a cleanup script's parent. Any pattern you pass appears in your own command line. Match on something the target has and you don't, or resolve PIDs and check /proc/pid/cmdline.
  • grep -c exits 1 when the count is zero. So $(grep -c x f || echo 0) emits two zeros and quietly corrupts a CSV column.
  • ps -eo pcpu is a lifetime average, not current load. It reported a stuck process at 86% that was actually consuming 140%. Sample /proc/pid/stat deltas over a few seconds instead.
  • SoapySDR ABI split. There are two installs on the Pi: /usr/local (ABI 0.8-3, airspy + sdrplay) and the distro's (ABI 0.8, rtlsdr + miri). xng links the distro one, so driver=sdrplay fails an ABI check and driver=miri segfaults at 2.5 MS/s. The RSP1A is effectively unusable with xng — moot, since it isn't in the ACARS path.
  • xng has no ppm correction for RTL-SDR. --max-ppm is VDL2-only. The ACARS dongle runs -p 2; at 131 MHz that's a 262 Hz offset, negligible for AM/MSK envelope detection, but there's no flag to match it.
  • RTL-SDR has a sample-rate gap between 300 kHz and 900 kHz. And for xng the rate must be an integer multiple of the mode's channel rate — 24 kHz for ACARS — where acarsdec wants a multiple of 12 kHz.

Not done

Open items

  • rtl_airband is down. Killed during CPU investigation and never restarted. It has no systemd unit — it was started by hand, so it will not come back on reboot. It used the RSP1A for ATC streams. If you want it on the new box, write it a unit this time.
  • None of this work is committed. The repo is clean at 26e0091; the entire investigation lives in /home/pi/acars-trial/, which is outside the repo and will not transfer with a git clone. Copy it manually if you want the harness.
  • xng's UDP output is unverified against the live web app. The CRC finding says it should be clean, but the end-to-end path — xng to web/server.py to the browser — has never run for more than a soak's duration.
  • The +55% figure comes from two channels only (130.025 and 130.450). 131.125 is weaker at −36.9 dB and its sensitivity advantage there is assumed, not measured.
